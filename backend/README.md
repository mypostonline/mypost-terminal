# MYPOST terminal backend

Локальный HTTP/WebSocket-шлюз между интерфейсом терминала и платёжным
оборудованием.

## Структура

- `src/config` — чтение и проверка переменных окружения;
- `src/api` — Express-приложение и HTTP-маршруты;
- `src/realtime` — WebSocket-подключения и трансляция событий;
- `src/devices` — драйверы карточных терминалов и купюроприёмника;
- `src/payments` — сценарии карточной и наличной оплаты;
- `src/bootstrap.js` — сборка зависимостей и жизненный цикл сервера;
- `src/server.js` — основная точка запуска;
- `scripts` — ручные аппаратные диагностические сценарии.

Тесты располагаются рядом с проверяемыми модулями и имеют суффикс
`.test.js`.

## Запуск

```sh
npm install
cp .env.example .env
npm start
```

По умолчанию HTTP-сервер слушает порт `3001`, а WebSocket доступен по
пути `/ws`.

## Настройка оборудования

Активность устройств и конкретный драйвер настраиваются независимо:

```env
CARD_TERMINAL_ENABLED=true
CARD_TERMINAL_DRIVER=vendotek

BILL_ACCEPTOR_ENABLED=true
BILL_ACCEPTOR_DRIVER=gpio-pulse
```

Для карточного терминала доступны драйверы `vendotek` и `mock`, для
купюроприёмника — `gpio-pulse` и `mock`. Переменная `VENDETEK_ENABLED` больше не
используется: универсальный флаг `CARD_TERMINAL_ENABLED` не привязан к
производителю оборудования.

## Фискализация наличной продажи через Vendotek

После приёма полной суммы backend может передать наличную продажу в Vendotek:

```env
CASH_FISCALIZATION_ENABLED=true
CASH_FISCALIZATION_PRODUCT_ID=1
CASH_FISCALIZATION_PRODUCT_NAME=WASH
```

Backend отправляет `IDL` с суммой продажи в копейках, событием `CSAPP`, новым
номером события и данными товара. Заказ получает состояние `completed` только
после ответного `IDL` с тем же номером события. При таймауте или разрыве связи
состояние становится `attention_required`: автоматически повторять передачу
нельзя, потому что первый запрос мог уже сформировать фискальный чек.

Фискализация поддерживается Vendotek с ПО EftVending или VTKPOS-V2 (Ф3). На
терминале и в TMS должна быть отдельно настроена облачная онлайн-касса. Поле
`CASH_FISCALIZATION_PRODUCT_NAME` допускает только ASCII, как требует протокол
VTK; код товара — от 1 до 6 десятичных цифр.

## Запуск без оборудования

Тестовый запуск читает общие настройки, включая таймеры, из `.env`, но
принудительно заменяет драйверы обоих устройств на `mock`:

```sh
npm run start:mock
```

Frontend запускается обычной командой `npm run dev`. На экране карточной оплаты
появятся действия «Одобрить оплату» и «Отклонить», а на экране наличной оплаты —
кнопки тестовых номиналов и «Внести остаток». Mock HTTP-маршруты доступны только
при соответствующем `mock`-драйвере и возвращают `404` в аппаратном режиме.

## Проверки

```sh
npm test
```

Аппаратная диагностика GPIO запускается отдельно и не входит в unit-тесты:

```sh
npm run smoke:bill-acceptor
```

## Приём наличных и сдача

Режим `gpio-pulse` использует те же проверенные параметры фильтрации импульсов,
что и `scripts/bill-acceptor-smoke.mjs`. Поддерживаемые номиналы задаются через
`BILL_ACCEPTOR_VALID_AMOUNTS`, по умолчанию это `50,100,500,1000` рублей.
Несколько купюр принимаются последовательно и суммируются в одной платёжной
сессии.

Разрешающая цепь купюроприёмника может управляться девятым реле платы из
`mypost-master`. Два разрешающих провода подключаются к сухим контактам `COM` и
`NO`; напряжение на них не подаётся. Настройки backend:

```env
BILL_ACCEPTOR_RELAY_ENABLED=true
BILL_ACCEPTOR_RELAY_URL=http://127.0.0.1:3181/bill-acceptor/relay
BILL_ACCEPTOR_RELAY_LEASE_MS=15000
BILL_ACCEPTOR_RELAY_RENEW_INTERVAL_MS=5000
BILL_ACCEPTOR_RELAY_REQUEST_TIMEOUT_MS=3000
```

`mypost-master` слушает этот API только на `127.0.0.1`, поэтому команда не
зависит от брокера и не выходит в сеть. Backend начинает приём импульсов только
после подтверждения мастера. Разрешение обновляется каждые 5 секунд; если
обновления прекратились, master автоматически размыкает реле через 15 секунд.
При запуске сначала должен быть доступен `mypost-master`, затем backend.

Таймеры наличной оплаты настраиваются отдельно:

```env
CASH_PAYMENT_BILL_TIMEOUT_SEC=120
CASH_PAYMENT_PARTIAL_DECISION_TIMEOUT_SEC=600
```

- таймер приёма запускается сразу после готовности купюроприёмника и
  перезапускается после каждой принятой купюры;
- таймер выбора запускается после остановки приёма при частично внесённой сумме
  и даёт пользователю время продолжить оплату или выбрать зачисление на баланс.

Каждая принятая купюра получает уникальные `id`, `sequence` и привязывается к
`sessionId` и `orderId`. При частичной оплате сессия переходит в
`partial_payment`, а купюроприёмник отключается до явного возобновления. После
истечения времени выбора сессия переходит в `balance_credit_required`. Кнопка
зачисления на баланс переводит успешно подготовленную сессию в
`balance_credit_ready`.

Если внесено больше суммы заказа, backend создаёт подписанную ссылку для QR-кода.
Для этого необходимо задать:

```env
CASH_CHANGE_CREDIT_URL_TEMPLATE=https://app.example.com/cash-change?token={token}
CASH_CHANGE_TOKEN_SECRET=replace-with-a-long-random-secret
CASH_CHANGE_TOKEN_TTL_SEC=86400
```

Ссылка ведёт во внешний мобильный или web-сервис, который фактически зачисляет
сдачу пользователю. Этот сервис должен проверить HMAC-SHA256 подпись и срок
действия токена, проверить `type=cash_change` и `amountMinor`, а также обеспечить
однократное зачисление по `sessionId`. Без URL или секрета терминал не показывает
неподписанный QR и просит вызвать оператора.

## Точки расширения

Новый HTTP-контракт добавляется отдельным модулем в `src/api/routes`.
Новый тип оборудования размещается в `src/devices`, а предметный сценарий,
использующий оборудование, — в `src/payments`.

Vendotek разделён на пять частей: `transport.js` обслуживает TCP-соединение,
`protocol.js` кодирует и разбирает фреймы, `commands.js` строит команды,
`payment-controller.js` управляет состоянием платёжной операции, а `client.js`
связывает их и предоставляет публичный API.
