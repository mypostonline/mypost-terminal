# СБП: контракт для бэкенда терминала

Это предлагаемый контракт, под который подготовлен фронт. Само подключение банка/платёжного провайдера на бэкенде ещё требуется. Фронт не содержит банковских ключей и не подтверждает оплату запросом `/orders/{id}/paid`.

## Включение

В данных поста вернуть `payment_methods: ["card", "sbp", "cash"]`. Также поддерживается объект `{ "code": "sbp", "enabled": true, "available": true }`; `available: false` отключает кнопку. Пока СБП не включена, остаётся неактивная плитка с фирменным логотипом.

Если API не возвращает `post.payment_methods`, используется `VITE_PAYMENT_METHODS=card,sbp,cash`. Массив из API имеет приоритет над env. Недоступный пост блокирует все способы оплаты. СБП не зависит от готовности локального карточного терминала и купюроприёмника.

Все маршруты ниже относятся к центральному `VITE_API_URL`, используют существующую авторизацию терминала. Необходима проверка доступа к заказу и посту на каждом запросе.

## 1. Создание заказа — существующий POST /orders

Разрешить `payment_method: "sbp"`. Остальная структура заказа не меняется. Цена, доступность услуг и итоговая сумма рассчитываются/проверяются сервером, а не доверяются данным браузера. Вернуть обычный заказ с `id`, `uuid`, `payment_method`, `total_amount`, `items`, `status`.

## 2. Создание или восстановление платежа

`POST /orders/{orderId}/payments/sbp`

Заголовок: `Idempotency-Key: terminal-sbp-{orderId}`. Тело: `{ "expires_in_seconds": 600 }`. Сумма, валюта, получатель и назначение берутся из заказа на сервере.

Для терминала задать срок оплаты **600 секунд (10 минут)** при создании QR у банка и вернуть соответствующий `expires_at`. Повторный запрос создания не продлевает исходный срок. Фронт ограничивает показ QR десятью минутами (или более ранним банковским `expires_at`), после чего запрашивает отмену и ждёт подтверждённого результата. Ограничения только в браузере недостаточно: срок действия банковского QR должен контролироваться сервером.

Создать динамический QR-код у выбранного банка/провайдера. Для одного заказа допускается один платёж: повторный запрос, перезагрузка экрана и конкурентные запросы возвращают тот же платёж, а не создают новые. Включая уже оплаченный или окончательно закрытый платёж. После окончательного отказа пользователь создаёт новый заказ.

Пример ответа (такой же формат используется для GET и отмены):

```json
{
  "payment": {
    "id": "sbp-payment-123",
    "order_id": 91,
    "status": "pending",
    "amount_minor": 125000,
    "currency": "RUB",
    "qr_payload": "https://bank.example/payment/opaque-token",
    "expires_at": "2026-09-18T12:05:00Z"
  }
}
```

`qr_payload` — реальная строка для кодирования QR от провайдера, не URL картинки и не ссылка на личный кабинет. Фронт использует существующий `/qr/svg?text=...` для её отображения. Этот маршрут должен поддерживать такую строку, не обращаться по переданному адресу, не кешировать персональные платёжные QR в общедоступном кеше и не записывать платёжные токены в логи.

`amount_minor` — целое число копеек, строго соответствующее итогу заказа; `currency` — `RUB`. `expires_at` — ISO 8601 с часовым поясом. В состоянии `pending` оба поля `qr_payload` и `expires_at` обязательны. В терминальных состояниях QR можно не возвращать.

## 3. Статус платежа

`GET /orders/{orderId}/payments/sbp`

Опрос фронтом — через 2 секунды после завершения предыдущего запроса, без параллельных запросов. Ответы не кешировать. Возможные статусы:

- `pending`: ожидаем оплату, уточняем результат у банка или завершаем обработку заказа.
- `paid`: банк подтвердил оплату; бэкенд надёжно сохранил оплату и обновил заказ.
- `canceled`: отмена подтверждена банком, неопределённого результата нет.
- `expired`: банк окончательно подтвердил истечение срока без оплаты.
- `failed`: окончательный подтверждённый отказ, не сетевой таймаут.

При `paid` обязательно вернуть рядом с `payment` поле `order` — полный актуальный объект заказа из GET `/orders/{id}`, включая `uuid`, `status`, `payment_method: "sbp"`, суммы, `items`, `change_amount` и `cashback_amount` при наличии. Статус заказа должен быть `paid` либо последующим (`sent`, `washing_wait`, `washing`, `drying_wait`, `drying`, `completed`). Только после этого фронт показывает итоговый экран с QR заказа и запускает его таймер возврата на главную.

Сбой получения статуса — HTTP 5xx/503, а не фиктивный `failed`. Пока результат не определён, пользователь остаётся на экране проверки и не должен платить повторно. После истечения локального таймера QR скрывается, но фронт продолжает проверку: часы браузера не подтверждают ни оплату, ни отмену.

## 4. Отмена

`POST /orders/{orderId}/payments/sbp/cancel`

Заголовок: `Idempotency-Key: terminal-sbp-cancel-{orderId}-{paymentId}`.

```json
{ "payment_id": "sbp-payment-123" }
```

Проверить принадлежность payment_id заказу, согласовать отмену с провайдером и вернуть ту же структуру. При подтверждённой отмене — `canceled`. Если деньги успели поступить, вернуть `paid` с актуальным `order`, а не отменять оплаченный заказ. Если отмена ещё обрабатывается — `pending`; фронт продолжает опрос. До подтверждения отмены заказ нельзя освобождать для новой оплаты. Сетевая ошибка отмены не означает успех.

## Обработка на сервере

1. Выбрать/подключить провайдера СБП, хранить его ключи только на сервере; использовать тестовый контур при разработке.
2. Хранить связь заказа, поста, платежа и идентификатора провайдера, сумму в копейках, валюту, срок действия и состояние.
3. Проверять подлинность входящих уведомлений способом выбранного провайдера. Не доверять редиректу, браузеру или произвольному POST как доказательству оплаты. При необходимости сверять статус отдельным запросом к банку.
4. Обрабатывать дубликаты и изменённый порядок уведомлений идемпотентно. Сверять сумму, валюту и получателя; не принимать несовпадающий платёж как оплату заказа.
5. При подтверждении оплаты транзакционно зафиксировать платёж, обновить заказ, инициировать предусмотренные системой чек/фискализацию, бонусы и запуск услуги ровно один раз. Повторные GET/POST не должны повторять продажу или запуск мойки.
6. Учитывать гонки оплаты с отменой/истечением срока. Оплаченный платёж не переводить в неоплаченный; поздние подтверждения требуют серверной сверки и установленного процесса обработки. Завершение отсчёта само по себе не даёт оснований для `expired`.
7. Обеспечить фоновую сверку с банком, даже если терминал закрыт/перезапущен или уведомление не дошло. Если заказ ещё не готов к итоговому экрану, вернуть `pending` без возможности повторной оплаты.

Ошибки: стандартный HTTP-код и JSON `{ "code": "sbp_unavailable", "message": "Оплата по СБП временно недоступна" }`. Отдельно различать отсутствие платежа (404), запрет доступа (403), конфликт состояния (409), недоступность банка (503). POST создания должен возвращать сохранённый результат при повторе после сетевой ошибки.

## Приёмочные проверки

Оплата и итоговый QR заказа; повторный POST/перезагрузка без второго платежа; двойной webhook без повторного запуска услуги; отмена одновременно с оплатой; потеря связи после создания и оплаты; просроченный QR и позднее подтверждение; несовпадение суммы/валюты; отключение СБП на посту; итоговый экран 120 секунд. Фронт не вызывает `/paid` и локальные `/api/card/*` для СБП.
